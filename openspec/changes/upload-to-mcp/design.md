# Design

## Context

Загрузка уже живёт в приложении: `upload::build_backend` строит бекенд из конфига на каждую загрузку, `AppController::handle_upload_request` (`src/app.rs`) — единственная точка входа, вызываемая колбэком кнопки Upload тулбара; ответ приезжает `MainJob::UploadFinished` через общий тик. Агентский канал (`/action`) маршрутизирует `AgentAction` в `agent_action`, MCP-мост пересылает форму действия в `/action` как есть — нового кода маршрутизации в мосте не нужно, только описания инструментов. Состояние редактора уже несёт флаг `uploading` (Cell в view, `set_uploading`), но наружу его не отдаёт.

## Goals / Non-Goals

**Goals:**
- Один кодовый путь для кнопки и агента: проверка конфигурации, состояние кнопки, запуск запроса.
- Статусная модель канала без сюрпризов для пользователя: агентские отказы не показывают модальных диалогов (та же логика, что у `agent_capture` с разрешением).
- Агент видит результат из канала: флаг `uploading` в `/state` для поллинга, URL в строке журнала `/log`.

**Non-Goals:**
- Новые провайдеры, очередь загрузок, прогресс с процентами — вне скоупа (как и в `upload-to-artifacts`).
- URL в ответе действия: действие асинхронное (`initiated`), URL забирается из журнала и буфера; отдельное поле в `/state` для последнего URL не вводится, пока поллинг + `/log` закрывают сценарий.
- Изменения `src/upload.rs` (транспорт, имена, прокси) не нужны.

## Decisions

### Один вариант `Upload` без аргументов
`AgentAction::Upload {}` (unit-подобная форма `{"Upload":{}}`) грузит именно тот снимок, что открыт в редакторе, — семантика кнопки. Загрузка произвольного файла по пути — отдельное расширение (это уже не «аналог кнопки»: путь может лежать вне папки снимков); сейчас оно не нужно, а `OpenEditor { path }` + `Upload` покрывают сценарий «загрузить существующий файл» двумя шагами.

### Отказы агента — `rejected`, диалоги не трогаем
Кнопка при не настроенном провайдере показывает модальный диалог (норматив `shot-upload` для пользовательского пути). Агентский путь проверяет те же условия заранее (`build_backend` → `None`, отсутствие редактора/снимка, загрузка в полёте) и возвращает `rejected` с причиной — по образцу `agent_capture`, который вместо модального NSAlert отвечает отклонением. Пользовательский путь (`handle_upload_request`) не меняется.

### Общий хвост `start_upload`
Из `handle_upload_request` выделяется общий хвост для кнопки и агента: `set_uploading(true)` → `upload_file` → откат состояния при локальной ошибке чтения. Кнопка сохраняет свой диалог, агент — свои `rejected`.

### Поллинг завершения — через `uploading`, результат — через `/log`
`EditorState` получает поле `uploading` (из уже существующего Cell). Строка успеха в `upload_finished` дополняется публичным URL (`upload: done, url: …`) — журнал и так несёт переходы загрузки, URL публичный, токен по-прежнему не выводится. Буфер обмена остаётся носителем URL по нормативу `shot-upload`, изменений там нет.

### Геттеры редактора вместо раскрытия ivars
Приложению нужны путь снимка и флаг загрузки: `EditorWindow` получает `shot_path() -> Option<PathBuf>` и `is_uploading() -> bool` — тонкие делегаты к view, в стиле существующих `set_uploading`/`agent_state`. Логика принятия решения остаётся в `app.rs`, где живут все агентские обработчики.

## Risks / Trade-offs

- Гонки «агент vs кнопка»: проверка «в полёте» и запуск не атомарны (оба на главном потоке, между ними нет `await` — фактической гонки нет; двойной клик кнопки уже закрыт её состоянием).
- URL в журнале виден всякому, кто читает `/log`; URL публичный по природе артефакта — принято (токен остаётся за границей).
- Мост и приложение из разных сборок: новое поле `uploading` в `/state` и новый вариант действия — надмножество старого протокола; старый мост с новым приложением работает, новый мост со старым приложением получит ошибку разбора действия — та же совместимость, что у всех прошлых расширений канала.
