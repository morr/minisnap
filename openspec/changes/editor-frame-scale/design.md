# Design

## Context

Сейчас канва редактора и есть кадр: `EditorView::draw` растягивает композит на весь свой bounds (`sx = bw/iw`), `pixel_point` переводит клики тем же отношением, а `refit_window` вписывает пиксели кадра как экранные точки (`fit_size` умеет только уменьшать) с полом по минимальной ширине тулбара. Следствия: Retina-кадр (2× пикселей) открывается вдвое крупнее, чем выглядел на экране; узкий кадр непропорционально растягивается до минимума тулбара (отношения `sx ≠ sy`).

Плотность дисплея известна в момент захвата: `capture_ready` (`src/app.rs`) получает `scale` (backing scale) и передаёт его оверлею, но к файлу и редактору знание не доезжает — `save_to_file` масштаб не принимает, имя масштаба не несёт.

Мотивация и границы — в proposal.md, норматив — в дельтах specs. Поведенческие решения подтверждены пользователем: светлая классическая шахматка, кадр по центру, суффикс `@2x` в именах ок.

## Goals / Non-Goals

**Goals**

- Кадр становится прямоугольником внутри канвы со своим масштабом показа; все переводы клик↔пиксель идут через него.
- Показ «как на экране»: 1:1 для обычных кадров, 50% для Retina, вписывание вниз для крупного, никогда не вверх.
- Плотность захвата записывается в имя файла (`@<n>x`) и читается из него при открытии.
- Светлая шахматная заливка пустот вместо тёмного фона.

**Non-Goals**

- Никакого зум-UI: ни кнопок, ни жестов — масштаб только начальный, по правилу из спеки.
- Формат PNG и содержимое буфера обмена не меняются; старые файлы не мигрируются и не переименовываются.
- Семантика команд Crop/Resize не меняется (они по-прежнему работают в пикселях кадра).
- Позиционирование окна (центрирование/якорь) не трогается — это change `editor-window-anchor`.

## Decisions

**1. Носитель плотности — имя файла.**
`save_to_file` принимает backing scale захвата; при `scale > 1` имя получает `@{round(scale)}x` между временн́ой базой и суффиксом коллизии: `MiniSnap_2026-10-31_12-00-00@2x.png`, коллизия — `...@2x_2.png`. При открытии снимка масштаб показа выводится из имени регуляркой `@(\d+)x` перед `.png`; нет суффикса — масштаб 1.
Альтернативы отклонены: pHYs-чанк PNG — наш энкодер его не пишет, сторонние инструменты (включая сам macOS) пишут ненадёжно; сайдкар в tmp-сессии — умирает с `/tmp` и не покрывает листание соседних файлов. Суффикс — конвенция macOS, файл самодостаточен.

**2. Масштаб показа считается один раз на показ кадра.**
`display_scale = 1/n` для `@nx`; итоговый начальный масштаб = `min(display_scale, вписывание в видимый экран)`. Прямоугольник кадра (позиция и размер в координатах канвы) и пиксельный размер изображения живут в ivars канвы, пересчитываются в `refit_window` при каждой смене кадра (открытие, листание, применённый кроп/ресайз). Промежуточные значения вроде «50%, но не влезло — вписали до 43%» допустимы: это вписывание, не зум.

**3. Вся геометрия — через прямоугольник кадра.**
`draw` рисует композит в прямоугольник кадра (клип по нему), `pixel_point` и `view_scale` считают отношения от прямоугольника кадра, а не от bounds. Это автоматически делает корректным размер новых элементов на Retina-показе: кегль текста `size_px * view_scale` при 0.5 даёт вдвое больший кегль в пикселях кадра — на экране элемент выглядит тем же, что на 1x-кадре. Служебная графика в экранных точках (маркеры `MARKER_RADIUS_PT`, ручки рамок, курсорные размеры) остаётся константой экрана и не масштабируется. Клик вне кадра прижимается к его краю — clamp в `pixel_point` уже есть, меняется только база.

**4. Шахматка — фон всей канвы.**
Светлая классика в духе Preview: две светло-серые клетки фиксированного размера в экранных точках (8–10 px), тайл готовится один раз и кешируется (пересоздание на каждый draw недопустимо). Тулбар и hairline не затрагиваются. Тёмный `BACKDROP` удаляется.

**5. `refit_window` без центрирования кадра по окну.**
Ширина окна = `max(минимум тулбара, ширина кадра)`, высота = кадр + тулбарная полоса; кадр центрируется в канве по обеим осям (вертикальный центрирующий запас появляется, только если пользователь вручную растянул окно по высоте). Позицию самого окна `refit_window` не меняет — пользовательское поведение якоря остаётся за `editor-window-anchor`.

**6. Именование при коллизиях и ретенции.**
Суффикс коллизии остаётся последним компонентом имени; `sorted_shots`/`latest_shot` работают по glob `*.png` и mtime — `@2x` внутри имени им не мешает (проверить тестами листинга). Редактор при пересохранениях имя файла не меняет, суффикс живёт всю жизнь файла; Crop/Resize не меняют плотность файла, масштаб показа пересчитывается от нового размера как обычно.

## Risks / Trade-offs

- [Дельта «Окно редактора» построена на пост-titlebar тексте требования] → `editor-system-titlebar` приземляется и архивируется первым; при перевороте порядка архивации текст дельты синхронизируется вручную перед архивацией.
- [WIP `editor-system-titlebar` лежит в тех же файлах (`app.rs`, `editor_window.rs`), включая временный debug-принт D4 внутри `refit_window`] → коммиты этого change — строго по своим правкам; debug-принт не удаляется (его уберёт titlebar).
- [Ретина-файлы, сохранённые до change, без суффикса] → показываются в 1:1, как сейчас; определить их плотность по файлу невозможно, миграции нет.
- [`bounds` читается как «кадр» не только в `draw`/`pixel_point` (рамки кропа, маркеры, тунер)] → при имплементации аудит всех использований `bounds`/`sx`/`sy` в `editor_window.rs`, каждый случай приводится к прямоугольнику кадра или к экранным точкам осознанно.
- [Шахматка удорожает отрисовку] → кешированный тайл; замерить при необходимости.

## Migration Plan

Без миграции данных и конфигов. Откат — revert коммитов change. Новые имена файлов (`@2x`) обратной совместимости не требуют: старый код читает их как обычные имена.

## Open Questions

Нет — все поведенческие решения зафиксированы с пользователем.
