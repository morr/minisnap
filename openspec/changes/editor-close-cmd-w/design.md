# Design

## Контекст

Закрытие окна редактора живёт в одном месте: обработчик `keyDown:` канвы `EditorView` (`src/editor_window.rs`, ветка keycode 12 + Command — ⌘Q, keycode 53 — Esc: отмена рамки, иначе закрытие). ⌘W (keycode 13) сейчас проваливается в пустую ветку `_`. Других путей закрытия у окна нет: приложение — accessory без меню-бара, оконных шорткатов через NSMenu не существует, системная красная кнопка работает через штатный `Closable` бит окна.

## Решение

- Расширить существующую ветку матча до `12 | 13 if Command`: ⌘W получает в точности поведение ⌘Q — `window.close()`, приложение живёт в трее. Одно место, нулевая новая механика.
- Альтернативы отклонены:
  - **NSMenu + `performKeyEquivalent`** — инфраструктура меню ради одного шортката в accessory-приложении; все существующие клавиатурные комбинации редактора (⌘Q, ⌘C, ⌘Z/⌘⇧Z) намеренно зашиты в канву, и вторая система маршрутизации только добавила бы разъезд.
  - **Переопределение `performKeyEquivalent` окна** — отдельный путь диспетчеризации для той же строчки кода; при first responder в текстовом поле он тоже не вызывается, выигрыша нет.

## Границы поведения (наследуются от ⌘Q)

- ⌘W закрывает окно и при активной рамке кропа/ресайза — рамку не отменяет, отмена остаётся за Esc.
- Во время ввода текста (поле — first responder) ⌘W до канвы не доходит и не срабатывает — то же ограничение, что у сегодняшнего ⌘Q.
- Конфигурируемость не вводится: комбинация зашита, как остальные клавиатурные комбинации редактора.

## Что сознательно не меняется

- ⌘Q и Esc: поведение без изменений.
- Глобальные хоткеи и конфиг: регистрации ⌘W нет, конфликтов нет — глобальные комбинации проекта живут на ⌘⌥-модификаторах, ⌘W доходит до приложения только когда окно редактора key.
- Системные кнопки и тулбар: владелец — change `editor-system-buttons`.

## Риски / компромиссы

- [⌘W не работает во время ввода текста] → осознанный компромисс, унаследованный от ⌘Q; закрытие в этом режиме остаётся доступным через Esc-коммит/отмену ввода и красную кнопку.
