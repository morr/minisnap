# Proposal

## Why

Окно настроек мелкое: `prefs.rs` отдаёт наружу сумку публичных контролов (кнопки-комбо, галочку, три поля провайдера), а всё его поведение живёт в `AppController` — wiring target/action, перерисовка заголовков строк, сохранение полей при каждом нажатии, ~200 строк знания об устройстве чужого UI. У проекта уже есть прецедент правильного шва — `ToolbarView` (`set_state(ToolbarState)` / `ToolbarEvent`). Заодно последовательность «хоткей изменился → config → реестр → 4 пункта меню → 4 строки» существует в двух экземплярах (`new` и `finish_recording`), а реестр `UPLOAD_PROVIDERS` в `prefs.rs` декоративен (`build` берёт `[0]`).

## What Changes

- Окно настроек проводит полный шов по образцу тулбара: наружу — `PrefsEvent` (клик строки-рекордера, записанная комбинация, переключение галочки, изменение полей), внутрь — `set_state(PrefsState)` (комбинации, строка в записи, видимость и значения полей). Внутрь переезжают: поведение строк-рекордеров, показ/скрытие полей секции, чтение и хранение значений полей.
- Локальный key-монитор рекордера ставится при старте записи строки и снимается по её завершении — жизненный цикл совпадает с записью, вместо процесса целиком.
- `AppController` получает один метод `apply_hotkeys(config)`: сохранение config, перерегистрация `HotkeyRegistry`, обновление пунктов меню; оба существующих вызова (`new`, применение записанной комбинации) сходятся в него.
- Декоративный реестр `UPLOAD_PROVIDERS` удаляется — один провайдер, честные поля; реестр вернётся в день второго провайдера.
- Контроллер остаётся владельцем `Config`; окно не читает и не пишет конфигурацию — только докладывает событиями.

Чистая перестановка: внешне наблюдаемое поведение (открытие/фокус окна, запись комбинаций, немедленное применение, сохранение полей, заголовок) не меняется — спеки не затрагиваются.

## Impact

- Спеки: не меняются (`skip_specs: true`).
- Доменный скилл `minisnap-shell` обновляется тем же change'ем.
