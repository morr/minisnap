# Proposal

## Why

Агент, работающий с запущенным minisnap, почти всегда делает цепочки последовательных вызовов: открыть редактор → выбрать инструмент → добавить несколько элементов → undo → закрыть окно. Сейчас каждый шаг — отдельный MCP-раунд-трип (`action`, `editor` по одному), и агент платит за каждый полным циклом вызова инструмента. Один batch-вызов, исполняющий цепочку по порядку, сокращает N раунд-трипов до одного и делает намерение («это одна последовательность») явным в вызове.

## What Changes

- Новый MCP-инструмент `batch`: упорядоченный список шагов, каждый шаг — объект ровно с одним ключом `{"action": <AgentAction>}` или `{"editor": <AgentEditorOp>}` — те же serde-формы, что у одиночных `action` и `editor`.
- Шаги исполняются по порядку против одного инстанса через существующие эндпоинты; ответ перечисляет статус каждого шага с его номером (`done` / `initiated` / `rejected` / `noop` / ошибка шага).
- Транспортная ошибка (инстанс умер, таймаут) останавливает оставшиеся шаги; ответ всё равно перечисляет исполненные шаги со статусами. Статусы шагов исполнение не прерывают — `rejected` одного шага не делает бессмысленными следующие.
- Описание `batch` и описания `action`/`editor` говорят агенту: несколько последовательных действий — предпочитай `batch`.
- Чтения (`state`, `screenshot`, `log`) и поллинг (`Capture` → опрос `state` → `OverlaySelect`) в batch не входят — они остаются одиночными инструментами; описание `batch` прямо предупреждает про асинхронность `Capture`.
- Лимит 50 шагов на вызов с читаемой ошибкой.

### Modified Capabilities

- `agent-control`: требование «MCP-сервер minisnap-mcp» — в список инструментов добавляется `batch` с правилом исполнения по порядку и остановки только на транспортной ошибке; одиночным `action` и `editor` предписывается отсылать агента к `batch` для последовательностей.

## Impact

- `src/bin/minisnap-mcp.rs`: новый инструмент в `tools_list()`, обработчик в `call_tool()`, юнит-тесты. Описания инструментов — тоже здесь.
- Приложение не меняется: `agent_proto.rs`, `agent_server.rs`, `app.rs` остаются как есть — шаги идут по существующим `POST /action` и `POST /editor`, теми же кодовыми путями, что и раньше. Перезапуск работающего minisnap не нужен, пересобрать надо только мост `minisnap-mcp`.
- Документация: `AGENTS.md` (раздел про minisnap MCP — инструмент и правило предпочтения), скилл `minisnap-shell` (список инструментов моста).
- Спеки: меняется только `agent-control`.
