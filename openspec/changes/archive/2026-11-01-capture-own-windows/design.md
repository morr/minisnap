# Design

## Context

Спека и код сейчас согласованы: исключение собственных окон закреплено и в спеке `frozen-capture` (требование «Клик по окну — окно целиком»), и в реализации — `visible_windows` (`src/capture.rs`) выкидывает из списка окон T0 всё, что принадлежит собственному pid. Мотивация правки — в proposal.md. Ключевой факт, делающий правку дешёвой: замороженный кадр дисплея собственные окна уже содержит — фильтр захвата строится через `SCContentFilter::initWithDisplay_excludingWindows` с пустым списком исключений, так что пиксели окна редактора в кадре есть, и клик-захват сводится к обычному кропу по фрейму окна.

## Goals / Non-Goals

**Goals:**

- Собственные видимые окна minisnap (редактор снимка, окно настроек) становятся целями клик-захвата на общих основаниях.
- Минимальная дельта: сузить исключение в спеке, удалить точечный фильтр в коде, синхронизировать скил `minisnap-capture`.

**Non-Goals:**

- Никаких изменений хит-теста, кропа и координатной арифметики: `topmost_window_at` и `window_frame_to_pixel_rect` работают с окном как с обычным SCKit-окном.
- Никакой отдельной защиты «захвата самого режима»: см. решение 2.
- Изменение поведения протяжки, отмены, переключения дисплеев и клика по чужим окнам.

## Decisions

**1. Убрать own-pid фильтр целиком, а не впускать отдельные окна по белому списку.**
`visible_windows` перестаёт сравнивать `processID` окна с pid процесса. Белый список («только окно редактора») отклонён: окно настроек ничем принципиально не отличается, а перечень пришлось бы поддерживать при появлении новых собственных окон. Общие условия видимости (layer 0, on-screen, есть владеющее приложение) сохраняются и применяются к собственным окнам так же, как к чужим.

**2. Отдельная защита оверлея не нужна.**
Исключение собственных окон исторически защищало от «захвата самого себя», но в момент T0 оверлея и вуалей ещё не существует — они создаются в `Overlay::show` уже после снимка, а повторный вход в режим захвата закрыт (`active`/`finishing` в оверлее и в `app.rs`). Окно на уровне `CGShieldingWindowLevel` к тому же не прошло бы общий фильтр layer 0. После завершения режима оверлей скрывается и перестаёт быть on-screen, так что в следующий T0 не попадает и он.

**3. Два инстанса ничего не меняют.**
Окна другого инстанса minisnap (например, редактора, запущенного из worktree) принадлежат чужому pid и уже сейчас попадают в список окон T0 — поведение для них не трогается.

**4. Скил обновляется в этом же change.**
Спека `agent-domain-skills` требует обновлять доменный скил в том же change, который меняет поведение домена: в `minisnap-capture` правится инвариант про состав списка окон T0 (убирается «pid != свой») и упоминание исключения в описании клик-захвата.

**5. Победитель клика: список окон T0 — из оконного сервера, рендер-проверка — подтверждением, фолбэк — верхнее окно.**
Живая эксплуатация вскрыла второй дефект того же клик-пути: список окон T0 не обязан совпадать с тем, что рисует композитор. Клики по видимому окну промахивались и доставались первому поперечному крупному окну: Chrome/WezTerm (2560×1410 — «весь экран»), Finder «mac-studio» (1425×1132 — «пол экрана»).
Первая ревизия (кандидаты из SCK-списка T0 плюс свежий перезапрос `SCShareableContent`, победитель по отрисовке, фолбэк — первое содержащее окно списка) живыми проверками оказалась недостаточной: записи `SCShareableContent` для окон, менявших размер вне штатного пути (winit/bevy-игра под оконным менеджером вроде loom), держат устаревшие фреймы и фантомные записи умерших состояний; свежесозданные окна отсутствуют в списке минутами; порядок списка не следует композитору; а нестрогий порог сравнения патчей (средняя разница < 16) ложно совпадал на тёмных плоских участках разных окон — терминал «совпадал» с игровой сценой за ним.
Итоговая механика (`resolve_click_target` в `src/capture.rs`):

- список окон T0 читается из `CGWindowListCopyWindowInfo` (`cg_visible_windows`): layer 0, есть владеющий процесс, только on-screen; фреймы и front-to-back порядок — данные оконного сервера, они совпадают с композитором (CGWindowList и AX согласованы, SCK — нет). Идентификаторы окон — общий с `SCWindow.windowID` namespace (`CGWindowID`), он и соединяет списки;
- `SCShareableContent` (свежий перезапрос в момент клика) используется только как источник `SCWindow`-объектов для рендер-проверки: окно рендерится отдельно (`SCContentFilter::initWithDesktopIndependentWindow` + `SCScreenshotConfiguration::setIgnoreShadows` + `SCScreenshotManager::captureScreenshotWithFilter`) и патч 7×7 px в точке клика сверяется с замороженным кадром; порог ужесточён до средней разницы < 8 — один и тот же контент через оба конвейера отдаёт разницу в единицы, несвязанные тёмные окна на строгом пороге расходятся;
- подтверждённый кандидат побеждает сразу; если проверка никого не подтвердила (анимированный контент меняется между T0 и рендером, или у окна ещё нет записи в SCK) — фолбэком берётся верхнее содержащее окно по CG-порядку; нет ни одного содержащего окна — весь кадр (клик по рабочему столу);
- клик не вызывает SCK синхронно на главном потоке: завершения SCK не доходят до main, заблокированного ожиданием ответа. Разрешение идёт фоновым потоком, ответ приезжает через канал, который тик приложения опрашивает на главном потоке (`overlay.poll_resolved_click`); до ответа оверлей висит, отмена (Esc/вуаль) сбрасывает ожидание.

Альтернативы: доверяться порядку SCK-списка — опровергнут живыми захватами; пиксельный хит-тест по замороженному кадру без списка — не отличает перекрывающиеся окна одного контента.

## Risks / Trade-offs

- [Клик по окну настроек теперь тоже захватывает окно, а не весь дисплей] → это ожидаемое обобщение нового правила, зафиксировано сценарием «Клик по окну minisnap» в дельте.
- [Пользователь мог полагаться на «клик по собственному окну = весь экран» как на способ снять весь дисплей при открытом редакторе] → весь дисплей по-прежнему доступен кликом по рабочему столу и протяжкой; поведение не теряется, а уточняется.
- [Кнопки чужих overlay-утилит (слои выше 0) остаются вне клик-захвата] → как и раньше: их отсеивает общий фильтр layer 0, отношения к этому change не имеет.
