# Design

## Выбранный подход

Аналог BRP: встроенный в приложение HTTP-сервер на `127.0.0.1` + отдельный бинарник `minisnap-mcp`, говорящий с агентом по MCP stdio и с приложением — по HTTP. Ничего между ними: ни AppleScript, ни синтетических CGEvent, ни `screencapture`.

Рассмотренные и отвергнутые варианты:

- **AppleScript / Accessibility** — кастомные view приложения не дают осмысленного AX-дерева (всё рисуется в drawRect), состояния документа там нет; клики по тулбару возможны, но это всё тот же синтетический ввод с тихими отказами.
- **CGEvent-эмуляция снаружи** (как делали сессии до сих пор) — двигает реальный курсор пользователя, клики молча не доходят до не-key окна, требует фокуса и Space; для pid-scoped ввода — недокументированное поведение.
- **Внешний наблюдатель** (`screencapture`, CGWindowList) — цветовые конверсии профилей, зависимость от Space, ноль доступа к состоянию документа; годится только как фолбэк для «взглянуть на весь экран».
- **Универсальный BRP из Bevy** — не переносится: minisnap не ECS; вместо реестра сущностей — свой набор endpoint'ов, отражающий реальную структуру приложения (окна, документ, журнал команд).

Решающий аргумент за in-app сервер: приложение и так имеет всё состояние в главном потоке и существующий насос `MainJob`/`tick` для доставки работы в него — сервер встраивается в этот механизм без единого нового примитива синхронизации.

## Потоки и доставка

- Серверный поток: `std::thread` с `TcpListener`, accept-цикл, один запрос за раз; разбор минимального HTTP/1.1 (GET/POST, Content-Length, `Connection: close`), JSON через `serde_json`.
- Исполнение в главном потоке: запрос упаковывается в `MainJob::Agent { request, reply: mpsc::Sender<AgentResult> }`; `tick:` (существующий, 50 мс) перекачивает и диспетчеризует `AppController::handle_agent`. Ответ уходит обратно по каналу; серверный поток ждёт с таймаутом (5 с) и отдаёт ошибку таймаута, не блокируя accept навсегда.
- Сериализация запросов естественная: всё исполняет один главный поток по порядку.

## Разбиение на модули

- `src/agent_proto.rs` — типы запросов/ответов (`serde`), идентичность экземпляра (`AgentIdentity`), тексты ошибок. Общий для приложения и MCP-бинарника: проект получает `src/lib.rs`, все модули переезжают под него, `main.rs` становится тонкой обёрткой, `minisnap-mcp` — второй bin.
- `src/agent_server.rs` — listener, HTTP-разбор, реестр экземпляров, отправка в `MainJob`.
- `src/logbuf.rs` — кольцевой буфер журнала (`Mutex<VecDeque<String>>`), макрос-обёртка над `eprintln!`; существующие вызовы переводятся на него.
- Диспетчер и сбор состояния — в `app.rs` (ему принадлежат ivars) с делегированием в новые публичные методы `EditorWindow` и `Overlay`.

## Endpoint'ы

| Endpoint | Что делает |
|---|---|
| `GET /state` | полное состояние: окна, редактор/документ, оверлей, конфиг, идентичность |
| `POST /action` | `capture {edit}`, `open_latest`, `open_editor {path}`, `close_editor`, `overlay_select {x,y,w,h}`, `overlay_cancel`, `prefs_open`, `prefs_close`, `quit` |
| `POST /editor` | `set_tool {tool}`, `set_color {rgba}`, `set_width {value}`, `command {…}`, `undo`, `redo`, `select {id}`, `page {dir}` |
| `GET /screenshot?target=composite\|window&path=…` | PNG в файл + путь и размеры в ответе |
| `GET /log?offset=…` | строки кольцевого буфера журнала |

Действия возвращают не только «принято», но и что произошло (`capture`: инициирован / заблокирован разрешением / оверлей уже активен; `editor`: применено / undo нечего / ошибка).

## Реализация по коду

- Состояние: `AppController::agent_state()` читает ivars (overlay `is_active`, editor, prefs, config) и вызывает новый `EditorWindow::agent_state()` — путь и файл снимка, элементы из `doc.elements()` с геометрией, выделение, инструмент, цвет/толщину, undo/redo, кадр окна.
- Действия редактора идут через `OpenShot::apply`/`undo`/`redo` и существующий sync (`redraw()` пересобирает тулбар и канвас) — тот же путь, что у мышиных обработчиков; файл и журнал сессии сохраняются автоматически.
- `overlay_select` — новый публичный метод `Overlay`: завершает сессию выделением заданного прямоугольника, вызывая тот же колбэк с `OverlayOutcome::Selected`, что пользовательская протяжка (кроп, звук, буфер, файл — без дублирования).
- `screenshot composite` — `render::render_composite` + `encode_png_atomic` в указанный файл; `screenshot window` — `cacheDisplayInRect` contentView'а редактора → `NSBitmapImageRep` → PNG; работает на перекрытом окне и в другом Space, цвет — ровно кодовые значения.
- Реестр экземпляров: каталог рядом с конфигом, по файлу на процесс `instances/<pid>.json` (pid, порт, exe, метка, время старта); запись снимается при выходе; мёртвые pid отбрасывает читающий. Файловых гонок слияния нет — каждый процесс владеет своим файлом.
- Порт: дефолт 15790; `MINISNAP_AGENT_PORT` > ключ конфига > дефолт. Конфиг: `agent-server-enabled: true` (дефолт), `agent-server-port: u16` (опционально) — старые конфиги читаются без правок. Занятый порт: явная строка в журнал, приложение живёт без сервера; путаницы инстансов нет, потому что идентичность проверяется по ответу.

## MCP-бинарник

`src/bin/minisnap-mcp.rs`, stdio: построчный JSON-RPC 2.0 (`initialize`, `tools/list`, `tools/call`, уведомления игнорируются), без async-рантайма — инструменты одношаговые. HTTP-клиент — `std::net::TcpStream`, короткие запросы. Инструменты: `instances`, `state`, `screenshot` (файл + base64-картинка в `content` типа `image`), `action`, `editor`, `log`. Конвенция qwe: инструмент никогда не паникует и не бросает — мёртвый экземпляр это короткий читаемый текст с `isError: true`; ответ всегда называет инстанс (метка + pid). Выбор инстанса: единственный живой — без вопроса; несколько — main, остальные перечислены в ответе; явный аргумент выбирает по метке или pid.

## Риски

- Занятый порт — решён явно (лог + продолжение без сервера, проверка идентичности).
- Таймаут главного потока (модальный диалог разрешения держит run loop, тик в нём продолжает работать — запросы не подвисают; блокирующий модальный код в tick-обработчике отсутствует).
- Крупные ответы (`/state` с сотнями элементов) — ограничений нет, элементы документа исчисляются десятками.
- `cacheDisplayInRect` на не-key окне — AppKit рисует view-иерархию вне экрана; подтверждается живой проверкой в tasks.
