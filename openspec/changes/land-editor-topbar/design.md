# Design

## Context

Ветка `editor-topbar` (HEAD `0ef5017`, линейный супerset стека `editor-restyle` → `editor-restyle-audit` → `editor-topbar`) отвечает от `2842ca3`; master с тех пор набрал 24 коммита: панель тюнера стрелки `MINISNAP_ARROW_DEBUG` в `src/editor_window.rs` (8 коммитов, оверлей канваса на `NSBox`) и эволюция отрисовки стрелки в `src/editor/render.rs` (4 коммита; ветка файл не трогала). Пробный `git merge-tree`: единственный конфликт — `src/editor_window.rs`; `Cargo.toml` (feature-флаги objc2-app-kit) и остальное мерджится автоматически.

Живой прогон ветки дал три корневые причины мёртвого функционала:

1. **Клавиатура.** `KeyableWindow` переопределяет селектор `canBecomeKey` — такого метода у `NSWindow` нет, AppKit спрашивает `canBecomeKeyWindow` (objc2-app-kit 0.3.2). Окно borderless не становится key (лог: `editor window: active=false key=false`), `keyDown` канваса не вызывается.
2. **Свотч цвета.** Кнопка — borderless `NSButton` с пустым титулом, без intrinsic content size; `NSStackView` сжимает её до 2×2 pt (подтверждено accessibility-инспекцией живого окна). Явный `setFrame(24×24)` затирается автолэйаутом стека.
3. **Слайдер толщины.** `WidthSliderView` — кастомный `NSView` без `intrinsicContentSize` и констрейнтов → нулевая ширина в стеке. Разделители зон (`bar_separator`, plain `NSView`) — та же болезнь.

Дефолтное состояние инструмента сегодня — `Some(Tool::Arrow)`: каждый клик по пустому месту канваса начинает рисование, поэтому «перенос окна протяжкой снимка» без смены дефолта невозможен. Спека уже знает состояние «без инструмента» (сценарий «Снятие выбора инструмента»).

## Goals / Non-Goals

**Goals:**
- Влить дизайн topbar в master без потери пост-форковых наработок master.
- Вернуть работоспособность клавиатуры, свотча и слайдера в новой вёрстке.
- Дать переносу окна за снимок однозначное правило разрещения конфликта «рисовать или двигать».

**Non-Goals:**
- Не переделывать отрисовку стрелки и тюнер (уже в master, приезжают стороной merge).
- Не трогать направления `editor-rail` и запаркованный `startup-permission-check`.
- Не менять палитру цветов, диапазон толщин, поведение undo/сессий.

## Decisions

### D1. Мердж git-merge, а не ребейз стека
`git merge editor-topbar` в master: один конфликт в `src/editor_window.rs` разрешается вручную — каркас окна и тулбар из ветки, блок тюнера (`arrow_tuner_panel` и его вставка под `MINISNAP_ARROW_DEBUG`) из master, панель остаётся оверлеем канваса с явными фреймами (конфликт чисто текстовый: обе стороны правили сборку окна в `EditorWindow::new`). Альтернатива — ребейз 16 коммитов стека — даёт те же конфликты 16 раз.
Критерий сохранности master: после мерджа `git diff master@{1}..HEAD -- src/editor/render.rs` пуст (стрелка не тронута), тюнер собирается и под `MINISNAP_ARROW_DEBUG` открывается.

### D2. Клавиатура — правильный селектор
Переопределение `canBecomeKey` переименовывается в `canBecomeKeyWindow` (`src/editor_window.rs`, класс `KeyableWindow`). Дешевле и надёжнее, чем `styleMask |= NonactivatingPanel` или подмена first responder: штатный путь AppKit для borderless-окон.

### D3. Intrinsic-размеры вместо явных фреймов
Свотчу, слайдеру и разделителям добавляются ширина/высота через autolayout-констрейнты к самим себе (либо `intrinsicContentSize` для `WidthSliderView` и разделителя). Явные `setFrame` из сборки тулбара убираются — в `NSStackView` они всё равно затираются. Кнопке-свотчу достаточно констрейнтов ширины и высоты: intrinsic у пустой borderless-кнопки не появится, но стеку достаточно явных размеров.
Проверка принятия: accessibility-инспекция живого окна (кнопка свотча ~24 pt, слайдер ~115×24, разделители 1×22) — тот же инструмент, которым диагноз поставлен.

### D4. Перенос за снимок — только в режиме просмотра
Правило разрешения конфликта «рисовать или двигать»: протяжка по канвасу переносит окно **только когда инструмент не выбран**; при активном инструменте канва рисует, как сегодня. Внутри `handle_mouse_down` порядок проверок: (1) рамка кропа/ресайза и её ручки, (2) поле ввода текста, (3) hit-test элементов и их маркеров (работают в любом режиме — клик по элементу в режиме просмотра выделяет и тянет его, окно не двигается), (4) если инструмент не активен — `performWindowDragWithEvent` и выход, (5) иначе — черновик рисования.
Дефолт меняется с `Some(Tool::Arrow)` на `None`; подсветка кнопок (`update_tool_highlight`) уже умеет состояние «ничего не активно» — сценарий «Снятие выбора инструмента» существует. После фиксации элемента инструмент остаётся активным (возврат в просмотр — повторный клик по кнопке).
Альтернатива «перенос всегда, рисование по удержанию/модификатору» отвергнута: ломает существующий сценарий «взял инструмент — рисуешь» и не просится спекой.

### D5. Зачистка worktree после мерджа, не до
Ветку `editor-topbar` нельзя терять до разрешения конфликта, поэтому четыре worktree (`~/develop/minisnap-editor-{topbar,restyle,restyle-audit,rail}`) и ветка `editor-rail` удаляются последним таском: `git worktree remove` + `git branch -D editor-rail` (изменения restyle/audit/topbar уже в master мерджем; rail не вливался сознательно).

## Risks / Trade-offs

- [Конфликт мерджа шире, чем показывает merge-tree (обе стороны двигали одни строки сборки окна)] → разрешать по принципу «хром из ветки, тюнер из master», после разрешения — `cargo build` и живой прогон обоих режимов (обычный и `MINISNAP_ARROW_DEBUG=1`).
- [Режим просмотра по умолчанию меняет привычный вход: раньше стрелка была сразу активна] → сценарий спеки «Открытие в режиме просмотра» фиксирует новое поведение осознанно; повторный клик по кнопке инструмента возвращает просмотр — выход в рисование всегда один клик.
- [Свотч без текста/иконки может потерять accessibility-размер даже с констрейнтами (пустая кнопка)] → констрейнты ширины/высоты обязательны (не intrinsic), accessibility-проверка из D3 — критерий приёмки.
- [Drag за снимок убирает «рисование первым же движением» для привыкших к дефолтной стрелке] → принято осознанно: просмотр — частый случай, рисование начинается с явного выбора инструмента (как в Monosnap).

## Migration Plan

Мердж коммитом в master (без промежуточных веток), фиксы — отдельными коммитами поверх по таскам. Откат — `git revert` мердж-коммита; состояние master до изменения отмечено тегом не требуется (история линейна в master).
